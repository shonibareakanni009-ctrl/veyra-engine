# Veyra Engine — Browser Prototype 001

**Status:** Source added; build and runtime validation pending.  
**Purpose:** Prove the first C++20, SDL3, and WebAssembly application path.

This is the first small executable experiment in the repository. It is deliberately not the full game engine.

## What the prototype does

- Starts SDL3 and creates a resizable application window or browser canvas.
- Uses SDL's callback-based application lifecycle.
- Draws a simple background, play area, and blue player square.
- Moves the square with W, A, S, D or the arrow keys.
- Moves the square to a mouse-click or touchscreen-press position.
- Uses elapsed time for movement so speed is not tied directly to frame rate.
- Uses a fixed logical 960x540 scene and letterboxes it when the display shape differs.

## What it does not do yet

- It does not contain Veyra's final renderer.
- It does not integrate bgfx yet.
- It does not implement scenes, entities, assets, physics, audio, Lua, or the editor.
- It does not establish verified support for every browser or device.
- It does not yet include automated runtime tests.

SDL_Renderer is used as a temporary bootstrap tool. The selected long-term rendering backend remains bgfx. This small first step is meant to prove the browser application lifecycle, input, and a visible frame before the more involved renderer integration begins.

## Required tools

- CMake 3.28 or newer.
- A C++20-capable compiler supplied by the Emscripten SDK.
- Emscripten SDK 6.0.10 for the pinned initial CI build.
- Ninja.
- Python 3, or another local HTTP static-file server, to serve the generated browser files.

SDL3 is downloaded by CMake as a pinned 3.4.18 source release. The archive SHA-256 is checked during download so an unexpected archive is rejected.

## Build for the browser

First install and activate the Emscripten SDK. The official installation instructions are:

https://emscripten.org/docs/getting_started/downloads.html

Open a terminal where the Emscripten environment has been activated, then run these commands from the repository root.

    emcmake cmake -S prototypes/browser -B build/browser-web -G Ninja -DCMAKE_BUILD_TYPE=Debug
    cmake --build build/browser-web --parallel 2

The output directory is:

    build/browser-web/bin/

It should contain:

- veyra_browser_prototype.html — the browser page.
- veyra_browser_prototype.js — the JavaScript loader generated by Emscripten.
- veyra_browser_prototype.wasm — the compiled WebAssembly module.

## Run locally in a browser

Do not open the HTML file directly with a file URL. Browsers commonly block the local loading of the separate WebAssembly file in that mode.

Start a static HTTP server from the repository root:

    python -m http.server 8000 --directory build/browser-web/bin

Then open this address on the same computer:

    http://localhost:8000/veyra_browser_prototype.html

To test on a phone connected to the same Wi-Fi, use the computer's local network IP address instead of localhost. The computer's firewall must permit the local connection.

## Continuous integration build

The repository workflow at .github/workflows/browser-prototype.yml builds this target on GitHub Actions and uploads the generated browser files as an artifact.

The workflow is a build check, not a public deployment. To run the artifact, extract it and serve the extracted folder through an HTTP server as described above.

## Manual validation checklist

The prototype is not considered validated until these checks are performed in real browsers:

1. The CMake configure step completes with the pinned SDL3 source.
2. The Emscripten build creates the HTML, JavaScript, and WebAssembly outputs.
3. The page loads over HTTP without browser-console errors.
4. The play area and blue square are visible.
5. W, A, S, D and the arrow keys move the square on a keyboard-equipped device.
6. A mouse click or touchscreen press repositions the square.
7. Movement remains stable when the window size changes.
8. The page remains responsive while frames are being rendered.
9. The browser can refresh the page and start the prototype again.

Record the browser, operating system, device, build revision, and result for each actual test. Do not mark a browser or platform as supported based only on a successful compile.
